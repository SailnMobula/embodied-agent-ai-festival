## An agent here is a configuration

Seven fields, saved under a name, activated with one click:

- **persona**, who the robot is, which language, how long the answers run
- **event**, where it stands today, opening hours, what to recommend to a child
- **self**, its body, its senses, its limits
- **voice**, **skills**, **start action**, **end action**

The three prompt blocks and the tool list are composed into one system prompt. The tool list is not
editable by hand: it is generated from the skills that are ticked.

## The path a sentence takes

<AgentPipeline />

1. Speech goes to the model directly, with no transcription step of our own
2. The model answers, calls a skill, or does both
3. The skill call reaches the robot, which dispatches the motion
4. The gate allows it or refuses it
5. The outcome goes back into the conversation, and the robot says what happened in its own words

Step 2 is the entire difference. Nowhere is there a list of situations.

## Activating an agent has three clocks

- **Prompt and tools** land on the running session, mid conversation
- **Voice, start action and end action** wait for the next session
- **`default`** is the builtin agent and cannot be edited, which makes it the way back when an event
  goes sideways

Every override is runtime only. Restart the robot's realtime service and the baseline from `.env`
returns, which is deliberate: a bad edit cannot survive the day.

## What still does not work

- The robot cannot walk to anyone, so every interaction happens where it stands
- A refused move is invisible unless `no_space` is configured, and its sound file is still missing
- Camera reads cost about three seconds, which is a long pause in a conversation
- The model is far too slow for balance, which stays in the low-level controller and is not up for
  discussion
- The same situation twice does not guarantee the same decision
